# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dachshund Dash is a single-page, vanilla-JS side-scrolling platformer. There is no build step, no bundler, no framework, and no `package.json` — the entire game logic lives in one file, rendered to a `<canvas>`.

- `index.html` — page shell: canvas, HUD elements (status pill, lives, run-summary pills, stage-tip callout, level-select overlay, mobile touch controls), all referenced by `id` from `game.js`.
- `game.js` (~6.7k lines) — everything: level data, physics, input handling, audio, rendering, and the game loop. All in global scope (no modules/imports).
- `styles.css` — all visual styling, including the mobile/touch and dark-themed level overlays.
- `assets/` — sprite-free game (drawn entirely in canvas via `drawX()` functions); this folder holds only audio (`.wav`/`.m4a` per-stage music and SFX) and a couple of images (`assets/henry/`, fonts).
- `scripts/run-https.sh` + `scripts/serve-https.js` — local HTTPS dev server (needed for iPhone tilt/motion APIs, which require a secure context).
- `tmp/` — scratch space used by past sessions for Playwright verification scripts (`verify-*.js`) and screenshots; not part of the shipped game.
- `changelog/` — dated PNG screenshots referenced from `CHANGELOG.md` entries.

## Running the game locally

No install step needed (no dependencies to fetch for the game itself).

```bash
python3 -m http.server 8080     # Option A
npx serve .                      # Option B
./scripts/run-https.sh           # Option C: HTTPS on :8443, for iPhone tilt controls (needs openssl)
```

Then open `http://localhost:8080` (or the printed HTTPS URL). There is no `npm run dev`/build/watch command — just serve the static files and reload.

## Linting / testing

There is no configured lint, typecheck, or test-runner command (no `package.json`, no CI config). The only correctness checks used in this repo's history are:

- `node --check game.js` — syntax-only sanity check after edits.
- Ad-hoc Playwright scripts (`node tmp/verify-*.js`, run against a locally-served instance, e.g. `http://127.0.0.1:8080`) that drive the page, assert on DOM/state, and save a screenshot into `changelog/`. `playwright` is not vendored in this repo — it must already be available (e.g. globally installed) to run these. A couple of `tmp/*.spec.js` files use `@playwright/test` instead of a plain script; there's no configured runner for these, so they were likely exercised with `npx playwright test` against a manually-started server.

When making a change, prefer this same pattern: `node --check game.js`, then a small Playwright script that sets `state`/`LEVELS` fields directly via `page.evaluate`, asserts on the resulting DOM, and screenshots the affected UI region.

## Architecture

Everything hangs off two global objects defined near the top of `game.js`:

- **`LEVELS`** (array, 20 entries) — the full level roster. Levels 1–2 and a handful of "themed" levels (3, 4, 5, 6, 7, 8, 9) are hand-authored literal objects with explicit `platforms`/`spikes`/`enemies`/`bones`/etc. arrays, then mutated in place afterward to bolt on a theme flag (`water`, `moon`, `volcano`, `giantEnemies`, `dark` + `lightSwitches`, `cloud`, `tunnel` + `tunnelEntrance`). The remaining levels are procedurally generated by `makeLevelTemplate(levelNum)`. Levels 10 and 20 are boss levels (`boss: { name, health, ... }`, "Corgi Captain" / "Corgi Overlord"). `levelRuntime` (set by `loadLevel()`/`hydrateLevelRuntime()`) is the live, mutable copy of the current level actually played against — never mutate `LEVELS[i]` during gameplay, only the runtime copy.
- **`state`** — all mutable run/session state: game `mode` (`start` → `title` → `playing` → `celebrating`/`paused`/`dead`/`gameover`/`won`), camera, lives/continues, timers for every timed ability (super jump, cape flight, bark cooldown, invulnerability, siren slow, tunnel dig boost, idle animations…), input tracking, and `state.dog` (the player's position/velocity/facing).

Runtime flow:

1. `loop()` is the `requestAnimationFrame` driver: `update()` then `render()`, forever.
2. `update()` branches entirely on `state.mode` — each mode (`start`, `title`, `paused`, `dead`/`gameover`, `celebrating`, `playing`) has its own early-return block. Only `"playing"` runs full physics/collision (movement, gravity, stomp/hit detection, boss AI via `updateBoss()`, siren/light-switch/tunnel-dig subsystems).
3. `render()` draws the whole frame: parallax background (`drawParallax()`, stage-themed), platforms/hazards/pickups, the dog (`drawDachshund()`), boss, HUD overlays (lives, ability icons, bones, level progress), and mode-specific overlays (`drawOverlay()` for title/pause/dead/win screens).
4. Input is wired via `setKey()` (keyboard) and a large block of touch-handling functions (`bindHoldButton`, `trackMobileTouch`, `syncMobileMovementTouch`, etc.) driving the same `state.keys`/`state.jump*` fields keyboard uses — desktop and mobile funnel into identical state.
5. Audio is manual `<audio>`/WebAudio management (`bgMusic`, `playX Sound()` helpers, `tone()` for synthesized beeps) — per-level background tracks are chosen by `levelMusicProfile(level)` based on the level's theme flags.

Level-select, HUD summary pills, and the "stage tip" callout are all derived from level data via a family of `levelSelect*`/`runSummary*` pure-ish formatter functions (e.g. `levelSelectGoalText`, `runSummaryTheme`, `levelSelectHazardPills`) — when changing what a level exposes (a new hazard/pickup type), these formatters are the place UI text/badges get derived from, not `index.html`.

A cheat code (typing `henry`) unlocks the level-select screen (`openLevelSelect()`); the buffer is tracked in `state.cheatBuffer`.

## Conventions from prior work (CHANGELOG.md / tmp/)

This repo's history shows a consistent per-change pattern worth following:
- Keep changes narrowly scoped to the files actually needed (usually a subset of `index.html`, `game.js`, `styles.css`).
- After a UI/behavior tweak, verify with `node --check game.js` plus a disposable Playwright script under `tmp/` that exercises the change and captures a screenshot into `changelog/` (dated filename, e.g. `changelog/YYYY-MM-DD-short-slug.png`).
- Append a dated entry to `CHANGELOG.md` (newest at top) describing what changed, which files were touched, how it was verified, and embedding the screenshot.
